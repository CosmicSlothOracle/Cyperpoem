1. Executive Summary

Purpose

This report provides a corrected, professional assessment of the host 165.232.131.154 based on original evidence collected during a lab exercise. The original report contained factual contradictions, misidentified services, inconsistent risk ratings, and improper use of security frameworks. This version restores integrity to the findings.

Overall Posture

The host contains two critical vulnerabilities (outdated FTP with anonymous access, and SMTP authentication bypass) that can lead to information disclosure, denial of service, and authenticated abuse. Internet-facing RDP and SNMP increase the attack surface. The HTTP service behaves as a catch-all honeypot, obscuring enumeration but still transmitting unencrypted data. The system is not suitable for production without immediate remediation.

Key Findings

  • FTP (TCP/21) – ProFTPD 1.2.10 (end-of-life, ~2005). Anonymous login enabled. Multiple confirmed CVEs (directory traversal, DoS, privilege escalation). Critical risk.
  • SMTP (TCP/25) – Authentication bypass (server returns 235 Authentication successful without credentials). No TLS enforcement. Critical risk (even though relaying to external domains is blocked, authenticated state can be abused).
  • RDP (TCP/3389) – Exposed to internet with standard TPKT/X.224 response. Brute-force and credential-stuffing surface. High risk.
  • SNMP (UDP/161) – Exposed; potential information disclosure. High risk if community strings default.
  • SOCKS proxy (TCP/1080) – Identified as SOCKS5 with username/password authentication (method 0x02). Credential strength unknown. Medium risk (pivot point).
  • HTTP (TCP/80) – No TLS, missing security headers, catch-all login page (likely honeypot or SPA). Medium risk (unencrypted traffic).
  • SSH (TCP/22) – OpenSSH 8.9p1 (current for Ubuntu 22.04). Password authentication enabled. Weak HMAC-SHA1 algorithms offered. Low risk (standard exposure).
  • VNC (TCP/5900) – Detected (protocol 3.8). No authentication observed. Low risk (unused service, low probability of compromise).
  • Port 9200 – Filtered / unresponsive to HTTP probes; not confirmed as false positive. Informational (needs further investigation).
  • Ports 1433, 1521, 9100 – Closed. Informational (corrected from original table).

What this report does not claim

  • SOCKS proxy credentials were not brute-forced or obtained.
  • SMTP relay to external domains is blocked (only local domains accepted) – the critical risk is the authentication bypass itself, not open relay.
  • Port 9200 remains indeterminate (filtered); no positive service identification.
  • No secrets were discovered by TruffleHog (though scan duration was implausibly short; re-run recommended).

2. Scope, Methodology, and Limitations

In Scope

Single host 165.232.131.154. TCP and UDP port scanning, service banner grabbing, protocol verification (RDP, SOCKS5), vulnerability scanning (nuclei), web directory fuzzing, and secrets scanning (TruffleHog). No exploitation or authentication bypass attempts (except passive verification of SMTP AUTH command).

Methodology

Aligned with OWASP WSTG practices for reconnaissance and service enumeration. Tools used: Nmap, naabu, ffuf, nuclei, custom Python probes, trufflehog, dig, nc, and Shodan (failed due to missing API key). Evidence files from the original assessment were re-examined for consistency.

Limitations

  • The host’s HTTP service returns 200 OK for every requested path (catch-all), preventing directory enumeration. Banner probe also showed an intermittent 500 Internal Server Error (Apache/2.4.6). This inconsistency was not resolved.
  • SOCKS proxy handshake: Nmap script confirmed username/password authentication, but protocol verification (custom SOCKS5 handshake) failed – this may indicate a non-standard implementation or a honeypot.
  • TruffleHog completed in 13ms for 1.96 MB of data – likely a local cache scan; remote secret scanning should be repeated.
  • No exploitation was performed; risk assessments are based on service exposure and known vulnerabilities.

5. Hardening and Remediation (Prioritised)

P0 – Immediate (Stop active breaches)

  • Disable FTP entirely – or replace with SFTP/FTPS with strong authentication. Remove anonymous access.
  • Fix SMTP authentication – require valid credentials (username/password) before returning 235. Enforce STARTTLS.
  • Restrict RDP – place behind VPN or IP allowlist; enable Network Level Authentication (NLA) and account lockout policies.

P1 – High-risk surfaces

  • Disable SNMP if not required; else change community strings to strong secrets and restrict source IPs.
  • Harden SOCKS proxy – rotate credentials, monitor logs for abuse, consider removing if unnecessary.
  • Add TLS to HTTP – obtain certificate, enforce HTTPS, add HSTS, CSP, X-Frame-Options, and other security headers.

P2 – Medium / defence-in-depth

  • Remove weak SSH MACs (hmac-sha1, hmac-sha1-etm@openssh.com) from /etc/ssh/sshd_config.
  • Disable VNC if not used; if required, add strong authentication and TLS.
  • Investigate port 9200 – use protocol-specific probes to identify service; block if unwanted.

6. Attack Chain (Possible)

Given the exposed services, an attacker could:

  • Anonymous FTP – read files, upload malicious content, or crash service (DoS).
  • SMTP bypass – authenticate as any user, send internal emails, potentially trick users.
  • RDP brute-force – if weak credentials exist, gain desktop access.
  • SNMP – leak system information (processes, users, network config).
  • SOCKS proxy – if credentials weak, pivot to internal network.

The most critical chains involve FTP directory traversal leading to configuration file disclosure, or SMTP bypass combined with RDP/SOCKS brute-forcing.
