Continuous Penetration Testing Project

Operational Scope & Report Guidelines — Target: CyberStepsVuln

"Learning without application is just reading. Let's break things."

Continuous Training Paradigm

Throughout this block, you will actively test and find real web application vulnerabilities, including SQL Injection, Cross-Site Scripting (XSS), Broken Access Control, CSRF, SSRF, XML External Entities (XXE), LFI, RFI, and WordPress Security Flaws.

Your objective is to execute a continuous, structured penetration test against a custom, deliberately vulnerable target environment called CyberStepsVuln. Rather than deferring analysis to the end of the term, apply your testing methodologies immediately following each technical session. You are expected to document all findings incrementally to build a professional-grade final deliverable.

This mimics standard industry engagement lifecycles. The final report is a technical portfolio piece demonstrating rigorous evidence collection, clear impact analysis, and practical remediation guidance.

The Target

Target Specifications

CyberStepsVuln is a custom, realistic virtual machine hosting a range of services, administrative interfaces, and hidden pathways designed to test diverse exploitation chains.

Setup Instructions:

  1. Download the virtualization archive: CyberStepsVuln.ova
  2. Import the image into your hypervisor (VMware / VirtualBox).
  3. Configure the network adapter to NAT mode (Subnet 10.10.10.0/24, matching your Kali Linux testing instance).
  4. Boot the target virtual machine.
  5. Access the initial web interface directly from your testing browser at: http://10.10.10.10

All active analysis and testing must be performed exclusively from your isolated Kali Linux virtual machine.

Operational Scope

A rigorous definition of scope separates authorized assessments from illegal network intrusions. Strict adherence to these boundaries is mandatory.

In Scope

  • Web Application: All hosted endpoints, parameter sets, forms, and input fields on 10.10.10.10.
  • Discovered Services: Any exposed TCP/UDP ports and daemons identified during host enumeration.
  • Vulnerability Classes: Injection flaws, server-side actions (SSRF/XXE), file inclusion (LFI/RFI), broken authentication, and session handling.
  • Content Management: Installed CMS platforms (WordPress, etc.) and active plugins.

Out of Scope

  • External Dependencies: Third-party CDNs, hosted libraries (Bootstrap, jQuery from external links), or external APIs.
  • Social Engineering: Phishing, credential harvesting, or physical coercion targeting instructors, classmates, or staff.
  • Physical Assessments: Facilities, hosting infrastructure, or networking equipment.

Note: Vulnerabilities identified in third-party CDN resources may be logged as auxiliary observations, but they do not constitute valid findings against the core application layer itself.

Structured Testing Methodology

Avoid chaotic testing. Apply a methodical, systematic process following each module session. The recommended analytical flow is structured below:

  1. 1 Reconnaissance & Footprinting: Enumerate open ports, identify server banners, and map general infrastructure technologies.
  2. 2 Directory & Path Mapping: Fuzz directories, discover hidden interfaces, and map all input parameters.
  3. 3 Input Validation Testing: Systematically test for SQL Injection (SQLi), Cross-Site Scripting (XSS), and Command Injection.
  4. 4 Authorization & Authentication: Probe session handling, cookies, token strength, privilege boundaries, and IDOR vectors.
  5. 5 File Handling & Parser Vulnerabilities: Enumerate Local and Remote File Inclusions (LFI/RFI), SSRF endpoints, and XXE injection vectors.
  6. 6 CMS and Third-Party Audits: Scan active content management systems for known, unpatched CVEs.
  7. 7 Post-Exploitation (Safe Limits): Pivot from initial access to confirm lateral movement possibilities and local host misconfigurations.

Utilize the official OWASP Web Security Testing Guide (WSTG) as your core technical checklist.

Project Deliverable & Reporting Standards

The primary deliverable is a comprehensive, client-ready security assessment document (PDF or DOCX format). It must bridge high-level operational risk with deep technical evidence, maintaining a professional tone throughout.

Minimum Requirements

  • Vulnerability Count: Minimum of 5 fully documented unique findings.
  • Replication (PoC): Clear, reproducible steps accompanied by annotated, high-resolution evidence screenshots.
  • Remediation: Actionable, specific programming or architecture level solutions for each finding.
  • Executive Briefing: A non-technical security health summary suitable for business stakeholders.

Required Document Structure

  1. Cover Page: Title, target, author details, date, and confidentiality status.
  2. Executive Summary: High-level summary, overall posture, and critical metrics without technical jargon.
  3. Scope & Methodology: Scope details, exceptions, and tools.
  4. Summary Table: Consolidated findings prioritized by industry-standard severities.
  5. Detailed Findings: Severity, affected components, PoCs, business impact, and specific fixes.
  6. Technical Appendix: Raw payloads, long-form system outputs, and standards.

Technical Guidance & Quality Tips

  • Write the Executive Summary Last: It is the single most visible page in the report. Summarize business impact plainly; avoid tool listings or specific CVE strings here.
  • Provide Actionable Remediation: Avoid generic advice. Instead of writing "Fix input validation", specify "Utilize parameterized prepared statements for the query at /search.php on line 42."
  • Do Not Dump Tool Outputs: Raw terminal dumps from scanners do not equal a finding. Explain what the output means, context-link it to the environment, and provide a clear narrative.
  • Document Continuously: Capture evidence and screenshots in real-time as you test. Finding replication is significantly more difficult after-the-fact.
