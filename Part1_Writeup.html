0. Reconnaissance Threat Metric (RTM)

To qualify the methodology, actions are tagged with the RTM (Risk/Yield). This framework evaluates the detection footprint against the potential intelligence value.

Risk (Detection Footprint)

  • 🧊 Icy: Zero/Near-zero footprint (OSINT, DB lookups).
  • 💧 Tepid: Standard background traffic (DNS/HTTP).
  • ♨️ Warm: Anomalous probing (UDP sweeps, 404s).
  • 🔥 Flammable: Loud, aggressive (Full port scans, fuzzing).
  • ☢️ Radioactive: Guaranteed SIEM/IDS alerts (Exploitation).

Yield (Intelligence Value)

  • 🥤 Soda: Low yield (Basic topology).
  • 🍻 Beer: Moderate yield (Structural routing).
  • 🍷 Wine: High yield (Surface narrowing, bulk assets).
  • 🍸 Absynth: Critical yield (Actionable compromise paths).
  • 🌌 Liquid-Schwartz: God-tier (Admin-level structural flaws).

1. Methodology & Tools

To achieve maximum coverage while adhering to strict verification rules, I implemented a hybrid pipeline combining professional open-source intelligence with custom targeted enumeration.

Phase 1: Passive Discovery

Level: Icy Wine 🧊🍷

I utilized a curated recommendation by agentic LLM ᯓKimK2.5ᯓ subfinder to query public sources (archives, search engines, transparency logs) without directly touching the target infrastructure. This provided a high-volume initial dataset. 

 CLI: 🕷🕷🕷 subfinder -dL domains.txt -all -recursive -silent -o subdomains_primary.txt 🕷🕷🕷

Phase 2: Active Enumeration

Level: Warm Absynth ♨️🍸

I instructed AI to create a custom Python tool, subdomain_enum.py, to perform targeted discovery. This script used a curated list of common prefixes to identify subdomains that might be missed by passive collection.

CLI: 🕷🕷🕷 python subdomain_enum.py -d domains.txt -o subdomains_bruteforce.txt -w 100 🕷🕷🕷

Phase 3: The Merge

Level: Icy Beer ❄️🍻

Results from both phases were merged, deduplicated, and strictly filtered. Crucially, I removed bare root domains

2. Verification Strategy

Level: Tepid Absynth 💧🍸
The Golden Rule: Every single entry in subdomains.txt has been actively verified against Google's Public DNS.

My custom verification logic (implemented in subdomain_enum.py) strictly followed the lab requirements:

  • Resolver: All queries were sent to 8.8.8.8.
  • Record Types: I specifically checked for A, CNAME, MX, and TXT records.
  • Filtering: Any domain returning NXDOMAIN wasdiscarded to prevent point deductions.

3. Interesting Discovery

While verifying thousands of subdomains, I discovered that Google's DNS resolver (8.8.8.8) is surprisingly resilient to high-volume queries if handled correctly.

By implementing a semaphore-based concurrency model in my Python script (limiting active workers to 100), I was able to verify over 20,000 candidates without triggering rate-limits or bans. This architectural choice was essential—without it, the resolver would likely have started dropping packets, leading to false negatives and a lower score.
